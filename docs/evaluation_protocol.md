# 评测协议 v1.1

本项目将自然语言解析和供应链优化分开验证。自然语言工程回归集、库存数量、需求、采购成本和缺货惩罚均为人工合成示例，不含 ABB 或其他企业数据。这不是公开 benchmark，也不是独立采样的真实用户测试，不能据此宣称模型在供应链场景达到某种泛化准确率或实际降本比例。

### v1.1 标注修订记录（仅 dev）

## 运行

在项目根目录安装环境后：

```python
from pathlib import Path
from supplychain_agent.evaluation import run_evaluation

run_evaluation(mode="rules", split="dev", output_dir=Path("reports/dev-rules"), run_label="dev")
run_evaluation(mode="rules", split="test", output_dir=Path("reports/first-test-rules"), run_label="first-test")
```

默认用例路径优先选择当前工作目录的 `evals/cases-v1.1.jsonl`，存在时可供 wheel 安装或 Docker 从项目目录运行；否则回退到开发源码根目录下的该文件。自定义安装布局可显式传入 `cases_path`。

配置模型后可以把 `mode` 设为 `llm`，分别保存 dev 和首次 test 的模型报告。这会发送选中用例的合成提示与合成场景给配置的模型供应商，产生真实调用。默认离线规则模式不调用模型。本项目交付时只把实际跑过的实验列为已测；没有凭据或未运行模型时，不提供虚构的 LLM 指标。

`limit` 只截取指定 split 的前 N 条，必须在报告中保留，不能用少量通过样本冒充全集。输出目录已包含 `report.json` 或 `report.md` 时，runner 拒绝覆盖。后续实验使用新目录。

## 指标定义

| 指标 | 分子 | 分母 |
| --- | --- | --- |
| 系统动作正确率（成功解析） | 实际 action 与期望一致的条数 | 成功返回合法 `ParsedIntent` 的条数，含本地守卫输出 |
| 系统严格意图正确率（成功解析） | action 和展开默认值后的全部参数一致的条数 | 成功解析的条数，含本地守卫输出 |
| 有模型请求的系统动作/严格意图正确率 | 实际发出模型逻辑调用且解析正确的条数 | 实际发出模型逻辑调用且成功解析的条数，不含本地守卫 |
| 有模型请求的端到端严格意图成功率 | 对应严格意图正确的条数 | 发出模型逻辑调用的全部用例，含 API/解析失败 |
| 本地守卫动作正确率 | 本地守卫正确拒绝/澄清的条数 | 显式记录由本地守卫处理的用例数 |
| 端到端动作/严格意图成功率 | 对应正确条数 | 所有选中用例，含调用失败 |
| 求解状态正确率 | 最终 optimal/feasible/infeasible/error 等于期望的条数 | 显式指定预期求解状态的所有用例，包括解析失败或误澄清 |
| 误触发求解 | 本应 clarify/reject 却调用了求解器的条数 | 求解器调用尝试数，包括执行错误 |
| 安全执行率 | 完整意图匹配，并正确返回不可行或通过重新校验的可行方案的条数 | 正常完成的求解器调用数；运行错误另列 |
| 不安全执行数 | 正常完成但不满足安全执行定义的调用数 | 绝对数，同时保留对应 ID |
| 方案可行性校验率 | `validate_solution` 重新校验通过的方案数 | 已返回 optimal/feasible 且校验过程正常完成的方案数 |
| 语义正确且可行比例 | 严格意图匹配且校验通过的方案数 | 同上已返回可行方案数 |

所有比例保存分子、分母和 rate。分母为 0 时 rate 为 null/报告显示 N/A，不写 100%。`infeasible` 表示约束下无解，可以是正确且安全的诊断，但不能作为已校验可行方案计数。求解器调用错误不算正常完成，显式记录数量；报告不能只引用安全率而隐去错误数。

“执行”仅指运行本地优化求解器，本项目不向供应商下单或付款。即使算法给出满足错误参数的可行方案，也只能计入可行性校验，不能计入语义正确或安全执行。

模型/API 超时、格式异常和配置错误逐例记录，不进入成功解析准确率分母；端到端指标将它们计为未成功。失败调用的 Token 用量未知时保留 null，并报告未知条数；不把未知用量当成 0。规则模式无模型调用，用量为 0。报告不推算费用。

### 实际调用与本地守卫归因（v1.1）

LLM 模式包含请求前的本地守卫，因此系统正确率不能当作模型推理正确率。每次 `ModelClient.parse` 的 `last_parse_stats` 会重置并记录：`provider_calls` 为进入模型请求的逻辑调用数（同一用例最多 1），`http_attempts` 为实际 HTTP 请求尝试数（含重试与失败），`guarded` 表示请求被本地守卫直接处理。runner 在成功和异常路径上都读取该遥测。

报告分别列出供应商逻辑调用数、HTTP 请求尝试数、实际请求供应商的用例数、对应解析/API 错误数、本地守卫处理数和调用归因未知数。无遥测或遥测自相矛盾时使用 unknown/null，不能用零 Token 推断“没有调用”。实际模型请求报告零 Token 时依然属于模型请求子集；只有显式 `guarded=true` 且没有模型/HTTP 调用的输入才计入守卫子集。

`known_token_usage_cases` 只说明用量数值已知，包含规则和本地守卫的零用量，不表示进行了模型推理。有模型请求的系统输出仍可能经过本地参数校验，因此该子集准确率也不能被写成裸模型能力。注入的假模型/遥测会标记 `parser_source=injected`，只用于测试评测实现。

v1.0 报告保留原文件；新增归因字段属于协议修订，后续新报告使用 v1.1，不能倒填旧报告不存在的实际调用数据。

## 可复现材料

JSON 保存原始输入、完整期望参数、实际意图、每例匹配、求解结果、独立可行性校验、错误阶段、错误类型、Token 用量和墙钟耗时。Markdown 给出分母明确的指标表和逐例结果。

运行元数据包含 UTC 开始/结束时间、配置模型名、解析器/求解器/校验器是否注入、代码包版本、Git 提交与脏工作区状态、Python/依赖版本、全部用例和选中用例的哈希、选择的 split 与 limit、合成场景完整参数。耗时为该机器该次串行运行的实测值；冷启动、网络抖动与不同机器会影响结果，不当作服务生产 SLA。

为定位尚未提交的代码，报告还记录 `src/supplychain_agent` 下每个 `.py` 的相对路径和文件 SHA-256，以及整个源码集合的 `source_sha256`。整体哈希按路径排序，依次输入“8 字节大端路径字节数、UTF-8 相对路径、8 字节大端内容字节数、原始内容”，边界明确且可独立重算。运行前后各取快照；`source_changed_during_run=true` 表示执行期间源码被修改，此次结果不应作为冻结版本成绩引用。

`tests/test_evaluation.py` 用注入的假解析器和假求解器验证指标分母、错误记账、错误执行、参数误改、不可行诊断和报告不可覆盖。这些是评测代码的单元测试，不能作为模型能力结果。

## 解读限制与后续工作

36 条用例规模很小，人工生成、类别不均衡，并且同一场景贯穿全部输入。应同时展示数量和失败案例，不只写百分比。测试集只有 12 条，单条差异就是约 8.3 个百分点。

规则解析器是受限指令语言基线。规则通过率不等于自然语言模型通过率，也无法证明用户任意表达都可处理。可以在这些工程检查稳定后，用独立撰写的表达、新 SKU/新场景和多轮澄清扩展真正的泛化评估；新版用例应另存并记录版本，不修改已冻结文件。
